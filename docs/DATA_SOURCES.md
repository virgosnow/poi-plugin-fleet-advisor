# 舰队参谋数据来源与同步

本文说明舰队参谋运行时使用的数据从哪里来、何时更新、保存在哪里，以及哪些结果只是参考。界面和 MCP 共用同一应用服务与数据视图；MCP 是访问入口，不是独立的数据来源。代码结构与执行流程见 [架构与维护](ARCHITECTURE.md)，第三方资料、许可证与来源版本见 [来源、依赖与权利声明](../THIRD_PARTY.md)。

## 来源分类

| 来源 | 含义 | 典型数据 |
| --- | --- | --- |
| 游戏响应，经 poi 整理 | poi 接收玩家正常游戏过程中返回的数据，舰队参谋从 poi 的内存状态读取 | 舰队、舰娘、装备、资源、入渠、游戏基础资料 |
| 插件主动读取游戏 | 舰队参谋在当前游戏会话中发起只读请求，结果用于插件自身视图 | 完整任务列表、演习、海域信息、游戏预设、远征项目状态 |
| 被动观察游戏事件 | poi 转发游戏真实请求和响应，插件按事件更新自己的观察结果 | 任务接取和领奖、出击战果、远征归航、演习战果 |
| 插件本地记录 | 插件从已确认事件产生并保存的数据，或玩家保存的设置、方案 | 任务目标细目、远征项目状态、演习历史、设置与方案 |
| 插件内置资料 | 维护时整理并随插件发布的数据及公式 | 任务条件、路线、敌情、远征规则、装备加成 |
| 插件推导或估算 | 综合上述输入计算的结果 | 索敌、制空、路线概率、远征收益、推荐与演习预测 |

同一数据可能既由自然响应更新，也由插件主动读取。主动读取的结果放在插件自己的视图中，不注入 poi 的 Redux 状态，也不伪造游戏响应。社区整理资料在开发或维护时更新，运行时不会为每次推荐实时查询 Wiki。

## 数据清单

| 数据 | 当前来源与更新 | 使用与限制 |
| --- | --- | --- |
| 账号身份 | poi 内存中的游戏账号资料；插件主动读取游戏基础资料并比对身份 | 用于会话和本地记录隔离；身份未确认时，任务和演习视图保持未知 |
| 舰娘与装备实例 | 游戏响应 → poi 内存 | 读取持有实例、等级、状态、属性、装备归属等；插件当前不主动重新拉取完整舰娘和装备列表 |
| 当前舰队、在航远征 | 游戏响应 → poi 内存中的舰队状态 | 包括舰位、远征状态、编号和预计返回时间；不是 poi 的任务计数，也不是插件主动读取的远征项目列表 |
| 资源、入渠及其他基础状态 | 游戏响应 → poi 内存 | 用于可用性、补给和筛选；资源缺失时为未知，部分缺失的列表在快照中以空列表或对象兜底，不能据此证明游戏中没有相关项目 |
| 游戏基础资料 | 游戏主数据 → poi 内存 | 舰娘、装备等基础属性与名称来自游戏主数据；装备适配优先使用 poi 选择器表，缺失时回退插件内置资料 |
| 任务列表、接取状态和粗略进度 | 游戏任务列表；自然响应或插件主动读取 | 游戏可返回未接取、进行中、已完成及 50%／80% 标记；经核实全分类、全部页面的数据才标记完整，自然响应提供完整列表时也可复用 |
| 任务目标和编成要求 | `data/quests/requirements.json`、限时任务资料与游戏任务列表匹配 | 出击、演习、远征共用经 Wiki 核对的本地任务资料；游戏是否开放和接取以实际返回为准。未收录目标保持未知 |
| 任务奖励 | 游戏任务列表和 `data/quests/rewards.json` 等参考资料 | 游戏给出的可选奖励优先；其他固定、可选奖励可引用内置资料，不能把参考资料当成游戏实际响应 |
| 任务卡显示 | 日文任务名称、结构化编成要求、行动目标、已观察进度及任务报酬 | 任务名称保持游戏原文；要求和报酬按界面语言显示，未知条件或进度不作推测 |
| 任务目标细目 | 插件观察真实出击、战斗和远征事件后写入 `quest-observations.json` | 是插件记录的已观察结果，不是服务器返回的各目标计数；断档无法证明某目标为零 |
| 海域进度与基地航空队 | poi 自然响应或插件主动读取 `mapinfo` | 数据放入插件只读视图；阶段未知时按可用资料展示或规划，不声称已解锁 |
| 游戏舰队预设 | poi 自然响应或插件主动读取 `preset_deck` | 游戏预设记录舰娘编成，不等同于包含装备的插件方案 |
| 远征项目状态 | 自然响应或插件主动读取 `mission`；本地缓存项目状态 | 用于项目开放、完成和月周期状态；不表示哪支舰队正在远征，也不等于某任务的目标计数 |
| 远征条件与收益 | `data/expedition_requirements.json`、`data/expedition_rewards.json` 及本地公式 | 条件、奖励和耗时主要依据日文 Wiki 整理；大成功概率和净收益为参考计算 |
| 演习对手列表和舰队 | 自然响应或插件主动读取对手列表与详情 | 可取得对手的提督名称、军衔、签名及公开舰娘、等级等；不提供对手真实装备。资料按账号和刷新周期保存在本地，舰队可能随时变化 |
| 演习战果 | 真实演习结果事件与插件本地 `practice-history` | 插件保存自己观察的结果；可选读取本机 `battle-detail/index11.csv.gz` 旧记录，但该文件不含可验证账号标识，不能作为当前账号任务进度，也不在演习页面当作账号历史展示 |
| 路线、攻略与敌情 | `data/normal_routes/`、`data/normal_route_guides.json`、`data/sortie/` | 带路规则及攻略、敌编成、血条为预先整理的参考数据；游戏实际当前阶段来自游戏状态 |
| 敌方雷击命中参考 | `data/sortie/enemy_accuracy.json`、[中文 Wiki 深海栖舰列表](https://zh.kcwiki.cn/wiki/深海栖舰列表)、[日文 Wiki 命中与回避](https://wikiwiki.jp/kancolle/命中と回避について) | 按敌舰编号及日文名称核对等级、运和装备命中；部分等级存在来源差异，固有雷击命中修正部分来自推测。冲突及缺失数据不导入 |
| 装备、战斗机制与加成 | poi 选择器表、`data/equipment_rules.json`、`data/asw_bonuses.json`、`data/combat_bonuses.json`、`data/installation_effects.json` 和计算代码 | 来源包括 Wiki 与其他开源资料；可能存在未确认条件，计算结果不等同游戏实际战果 |
| 地图图片 | 插件地图缓存、poi 资源读取器或 poi 磁盘缓存；缺失时尝试游戏服务器或资料中配置的备用地址 | 先核对图片尺寸与哈希再使用和缓存；坐标索引和公共素材随插件提供 |
| 控件与画面识别 | 游戏当前渲染树；必要时游戏视口截图与插件内置识别模板 | 用于明确授权的编成、换装及状态核对；识别结果不是游戏服务器返回的账号资料 |
| 推荐、路线概率、制空、索敌及战况预测 | 插件从游戏数据与内置规则计算 | 路线概率不包含战斗撤退；有界推荐不保证最优；演习对手参考配装不是真实装备，战况分布不是实测胜率 |
| 草稿、设置与保存方案 | 工作台内存及插件自己的持久化文件 | 草稿与游戏真实舰队、游戏预设分开；设置和已保存方案来自玩家操作 |

账号资料通过 [`src/host/store.js`](../src/host/store.js) 读取；后台数据视图由 [`index.js`](../index.js) 组合。查询和推荐不改变游戏，执行编成或换装走单独的预览、权限和核对流程。

## 主动读取的游戏接口

| 接口 | 数据 | 时机与边界 |
| --- | --- | --- |
| `/kcsapi/api_get_member/basic` | 游戏账号基础资料 | 当前会话首次验证时比对 poi 账号；读取器只向插件返回身份是否匹配 |
| `/kcsapi/api_get_member/questlist` | 任务列表 | 以全部分类分页读取；登录、数据不完整或请求查询时可触发。分页过程中状态变化会放弃本次结果 |
| `/kcsapi/api_get_member/mapinfo` | 海域进度与基地航空队 | 登录后缺失时同步；相关自然操作可能触发重新读取 |
| `/kcsapi/api_get_member/preset_deck` | 游戏内编成预设 | 登录后缺失时同步；预设发生相关变更后刷新 |
| `/kcsapi/api_get_member/mission` | 远征项目列表和状态 | 登录后、月周期变化或远征归航后按需刷新；不是舰队在航状态 |
| `/kcsapi/api_get_member/practice` | 演习对手列表 | 演习页面激活且没有当前周期缓存时按需同步 |
| `/kcsapi/api_req_member/get_practice_enemyinfo` | 指定对手的公开舰队 | 演习页面激活时，对缺失或已超过 5 分钟的资料逐个读取；不包含其真实装备 |

实现见 [`src/host/quest_reader.js`](../src/host/quest_reader.js)、[`src/infrastructure/sync/read_scheduler.js`](../src/infrastructure/sync/read_scheduler.js)、[`src/infrastructure/persistence/basic_data_sync.js`](../src/infrastructure/persistence/basic_data_sync.js)、[`src/infrastructure/quests/quest_auto_read.js`](../src/infrastructure/quests/quest_auto_read.js) 和 [`src/infrastructure/practice/practice_sync.js`](../src/infrastructure/practice/practice_sync.js)。

读取通过当前游戏帧内的原生请求执行，使用当前会话；插件不把账号令牌作为任务记录保存。任务、演习和基础资料共享队列，读取事务串行并合并重复请求；队列中的读取事务默认至少间隔 250 毫秒，任务分页属于同一事务。游戏操作、会话变化或不满足读取条件时，正在进行的读取可能中断或延期；失败后会退避重试。任务和基础资料登录后自动同步；演习资料在插件的演习页面激活时按需同步，无需打开游戏中的演习画面。

插件在登录前启动、登录后启动和热更新后重新启动时都会重新判断会话；账号或页面会话变化会使旧同步上下文失效。插件卸载期间无法保证观察到全部游戏事件，已有数据只有在满足对应账号、会话和新鲜度条件时才会被恢复或再次校验。队列和交互保护降低干扰，但不能证明与游戏已有网络活动绝无并发。

## 任务目标和远征的计数依据

游戏返回的进度标记与插件观察的细目是两层信息。多目标任务的 50%／80% 通常不能指出具体完成了哪一张图或哪一次远征；插件只能记录自身确认过的目标，未观察的历史显示为未确认，而不是强行补零。

远征计数由插件观察真实的远征结果：先从出发事件或 poi 当前舰队的在航信息识别航次，在归航结果到来时判断成功级别、远征编号及当时已接取的任务。任务可以在远征出发后、归航前接取；插件重启后也可根据仍在航的舰队恢复观察。在已观察的会话及安全交接范围内，航次和事件去重用于避免重复计数。插件未运行、账号会话未确认或结果事件缺失时，仍可能出现无法恢复的细目。

特定任务可以在游戏标记与任务定义足以唯一确定数量时做只读推断。例如 D39「西方連絡作戦による航空技術獲得」只有 30 号远征成功两次这一目标，游戏显示 50% 对应 1/2；该推断不写成一条额外的归航事件。不能将这一规则推广到多目标任务。

poi 自身有部分任务子目标追踪，另有插件可能保存远征历史，但它们并不保证覆盖全部任务、账号、周期和接取状态。舰队参谋当前不把 poi 的任务细目或阿卡西远征历史自动累加为自己的任务计数。可选读取的旧演习战斗记录也不提供可验证账号身份。相关实现见 [`quest_progress_observer.js`](../src/infrastructure/quests/quest_progress_observer.js) 和 [`quest_progress.js`](../src/infrastructure/persistence/quest_progress.js)。

## 本地持久化与缓存

插件用户数据根目录为 `~/.poi-plugin-fleet-advisor/`，其内容不是游戏服务器的原始数据：

| 位置 | 内容与作用 |
| --- | --- |
| `quest-observations.json` | 按账号哈希、任务和周期保存插件观察的任务目标进度 |
| `expedition-status/` | 按账号哈希保存远征项目状态及月周期信息，不是航次或任务计数 |
| `practice-history/` | 按账号哈希保存插件观察到的演习结果（最多 100 条）及当前刷新周期的对手名称、军衔、签名和公开舰队资料 |
| `mcp-state.json` | 插件设置、MCP 与自动操作权限及执行任务相关状态 |
| `recommendation-cache/` | 推荐、底层计算和诊断等缓存；可依设置清理 |
| `map-cache/` | 校验过的地图图片缓存，不保存账号状态 |

统一日志目录为 `recommendation-cache/logs/`，可在插件设置中清除；旧安装目录下的运行日志在插件加载时迁移。可选旧演习历史来自 poi 数据目录的 `battle-detail/index11.csv.gz`；该文件不是舰队参谋的账号隔离记录。清理缓存可能移除本地记录，不能当成从游戏服务器恢复历史明细的手段。

## 维护数据来源时

新增或调整数据时，应同时确认：实际获取路径是 poi 状态、自然响应、主动请求、本地文件还是内置资料；数据能否跨账号、重登或周期复用；自然响应和主动结果如何处理先后顺序；缺失或断档应如何显示；对用户提供的是游戏事实、已观察下限还是参考估算。修改第三方资料还应同步维护 [来源声明](../THIRD_PARTY.md)及对应数据文件中的来源和版本信息。
